A useful engineering website needs more than a chronological list of posts. A reader may want an ordered introduction to a subject, an explanation of a concept, or a troubleshooting example. These are different entry points into the same knowledge. This repository models that knowledge once and builds several static views over it.

This article describes the implementation in this repository. It uses Astro 5, strict TypeScript, Markdown, pnpm, Pagefind, and GitHub Actions. The output consists of HTML, CSS, a small amount of browser JavaScript, search index files, and XML/text feeds. There is no deployed application server, database, account system, or remote search service.

“Zero-cost” describes the intended public GitHub Pages hosting setup: the platform requires no paid infrastructure. It is not a guarantee that every use of GitHub, every traffic level, or an unrelated cloud project is free. GitHub documents the availability and limits of Pages in its [official Pages documentation](https://docs.github.com/en/pages/getting-started-with-github-pages/using-custom-workflows-with-github-pages). The separately featured AI SRE Platform is an architecture **lab**, not evidence that this knowledge platform operates production infrastructure.

## Start with a reproducible local build

Use Node.js 22.12 or newer and pnpm 10.32.1, which is pinned in `package.json`. After cloning this repository, run:

```bash
pnpm install --frozen-lockfile
pnpm run content:validate
pnpm run test
pnpm run check
pnpm run build
pnpm run test:build
pnpm preview
```

The frozen install checks the committed dependency lockfile. Content validation runs before Astro's production build. `check` runs both Astro diagnostics and TypeScript's no-emit check. `build` creates `dist/` and then runs Pagefind over that output. `test:build` verifies generated pages, internal resources, canonical URLs, sitemap, RSS, and robots.txt against the configured hosting base.

`pnpm dev` is useful for editing, but Pagefind's index is generated by the production build. Use build followed by preview to test search. On Windows, if pnpm is not on PATH, the equivalent command is `corepack.cmd pnpm`. The helper `scripts/validate-all.ps1` runs the five required commands plus generated-output checks through Corepack. Run `test:collections` and `test:browser` separately for integration and Chromium coverage.

## Model five entities, not five copies of an article

The content source has this structure:

```text
src/content/
  articles/en/                 Markdown with YAML frontmatter
  articles/zh-tw/              Translated Markdown
  topics/                     JSON taxonomy entries
  skills/                     JSON learning dependency entries
  learning-paths/             JSON ordered article membership
  projects/                   JSON project relationships
```

The five entity schemas are defined in `src/content/schemas.ts`. The command-line validator and Astro Content Collections share these schemas. The schemas are strict: unexpected metadata is an error instead of being silently discarded. This implementation supports Markdown Articles and JSON data entities; it does not install an MDX integration.

Three Article fields have different purposes. `id` identifies one physical content entity and is used by graph relationships. `translationKey` groups equivalent language versions. `slug` controls the public path. This article's English and Traditional Chinese versions have different IDs and one shared translation key. Renaming the slug must not require rewriting every LearningPath or Project reference.

A Topic is a browsing category such as Platform Engineering. A Skill describes a learning dependency or capability. Keeping them separate lets a reader browse a broad category without pretending that the category itself is a prerequisite. The initial taxonomy is deliberately shallow.

## Give each relationship one owner

Articles own their Topic references, Skill references, prerequisite Skills, and recommended Articles. LearningPaths own their ordered Article lists. Projects own their related Articles, featured Skills, and related LearningPaths.

For example, the `knowledge-platform` LearningPath contains a section whose `articleIds` list includes both translations of this article. The page filters that list by language and publication status while preserving its order. It does not reorder articles by title or publication date.

An Article must not contain `order`, `level`, `learningPaths`, `projects`, or `estimatedMinutes`. The first four would create competing ownership or ambiguous semantics; reading time is derived instead. A positive integer `estimatedMinutesOverride` is the supported exception to the reading-time estimate.

`reverseIndexes()` in `src/utils/graph.ts` computes incoming relationships. Given an Article ID, the site can find the LearningPaths and Projects that reference it. Given a Skill ID, it can find referencing Articles, dependent Skills, and Projects. The code deduplicates these memberships without changing the source lists. The graph stays in build-time memory; the browser does not receive a graph-processing application.

## Validate raw content before loading it into Astro

A loader stores entries under IDs. If two source files use the same ID, a keyed store can hide the duplicate. The repository therefore reads the original files before Astro ingestion. `src/utils/content-source.ts` preserves every entry, records its source path, parses the metadata, and checks IDs before schema validation can discard invalid records.

The V1 validator treats these as hard errors:

- Duplicate IDs within each of the five entity types.
- Missing Article Topic, Skill, prerequisite Skill, or recommended Article references.
- Missing LearningPath Article references.
- Missing Project Article, Skill, or LearningPath references.
- Forbidden Article fields, malformed content, or schema failures.

The CLI returns a nonzero exit status for errors. Warnings have stable IDs and do not fail the command. They cover missing Article Topics or Skills, published Articles outside LearningPaths or Projects, referenced deprecated Skills, and translation groups with only one locale.

This article intentionally has no Project membership: describing the knowledge platform does not make it part of the AI SRE lab. Its `W_ARTICLE_NO_PROJECT` warning is informative. Adding an unrelated Project reference just to eliminate that warning would make the content less accurate.

Skill dependency cycles, Topic parent cycles, supersession cycles, empty LearningPath sections, and complex translation validation are not V1 blockers. This boundary is explicit in the architecture documentation and tests.

## Build localized views with one canonical Article route

Astro statically generates `/zh-tw/` and `/en/`, with Start, Learn, Topics, Blog, Cases, Projects, About, and Search sections. Topic, LearningPath, and Project detail pages are aggregators. They link to the canonical Article rather than rendering a second full copy.

`tutorial`, `concept`, `reference`, and `opinion` Articles use `/blog/:slug/`. `troubleshooting` and `case-study` Articles use `/cases/:slug/`. The URL helper also adds the locale and deployment base. Only Articles with `status: published` produce public pages; drafts and archived records remain available to validation but do not enter public lists, feeds, or search.

Language navigation uses translation keys for Articles. A published equivalent takes the reader to its own slug and content-type route. If no published equivalent exists, the language link falls back to the target locale's home. SEO alternate links include only actual published equivalents. The language chooser and both homes form a reciprocal cluster with the chooser as `x-default`. Shared entities have one stable ID; Traditional Chinese display text is namespaced by collection and owning path in `src/i18n/content.ts`. Missing labels warn and fall back to source text; stale translation keys fail validation. Audience and maturity display text is localized without changing relationship ownership. Article pages and cards omit difficulty.

The homepage presents the author's personal technical blog: Hero, About This Blog, latest Articles, featured Project, Article Series, featured Topics, latest Cases, and About the Author. Article Series use the existing LearningPath model. Empty sections say that nothing has been published. No invented incident report or employment history fills an empty state.

## Add theme controls and static search

Theme preference has exactly three states: light, dark, and system. No saved preference means system. A small inline head script resolves the initial color scheme before the page paints. The browser controller persists explicit choices, reacts to OS changes, and continues working if storage is blocked. CSS also respects the OS when JavaScript is disabled.

Navigation uses semantic links, wraps on narrow screens, and stays available without JavaScript. The layout has a skip link, visible keyboard focus, language labels, and a native theme selector. Article headings feed a static table of contents; there is no React hydration for these controls.

Reading time is calculated during the build: Han characters contribute at 400 characters per minute and other words at 200 words per minute. The contributions are added, rounded up, and given a one-minute minimum. Fenced code, HTML tags, and Markdown link/image destinations are excluded. This estimate remains in build-time data and is not displayed on Article pages.

Pagefind indexes the main content of canonical Articles and Topic, LearningPath and Project detail pages, including titles, descriptions, bodies, and Topic and Skill names indexed through data-pagefind-index-attrs. Article pages omit the visible classification panels. Homes, section indexes, the language chooser, navigation and the search UI are excluded. The search page loads local Pagefind assets only. Its bundle and result paths include the deployment base. Pagefind creates separate language indexes; the current build reports that `zh-tw` stemming is unavailable, so matching does not expand across linguistic root forms. Browser tests exercise actual queries and result navigation in both locales.

## Generate SEO and feeds during the build

The shared layout emits a title, description, canonical link, Open Graph metadata, a social image, locale alternates, and an RSS discovery link. Canonical Article pages include escaped JSON-LD: `TechArticle` for technical types and `Article` for opinion pieces. JSON serialization escapes `<` so content cannot terminate the script element.

Astro's `sitemap.xml.ts`, `robots.txt.ts`, and localized `rss.xml.ts` files are build-time endpoints. They generate static files; they are not deployed backend APIs. RSS uses stable Article IDs as GUIDs, canonical URLs as links, localized channel titles and absolute Atom self links. Published Article route collisions fail content validation with both source files named; sitemap generation retains a final uniqueness check. The generated robots file permits standard crawlers and OAI-SearchBot and points to the configured sitemap. Under project-site hosting, crawlers consult the origin-root robots file, so `/Blog/robots.txt` alone does not configure crawler policy or sitemap discovery. The maintainer must configure the owner site's root robots file and sitemap directive before publication; local validation checks only generated text.

## Treat GitHub Pages origin and base separately

For a user site, the origin might be `https://username.github.io` and the base `/`. For a repository site, the same origin uses `/repository-name/`. Setting only the origin is insufficient: links, CSS, scripts, search results, feeds, and social metadata must agree on the base.

PowerShell example:

```powershell
$env:SITE_URL = 'https://username.github.io'
$env:SITE_BASE = '/repository-name/'
corepack.cmd pnpm run build
corepack.cmd pnpm run test:build
```

`SITE_URL` accepts an HTTP(S) origin, not an origin with a repository path. `SITE_BASE` is normalized separately. Local builds default to `http://localhost:4321` and `/`. In CI, `scripts/configure-pages.ts` derives the settings from `GITHUB_REPOSITORY`, including the special owner-site repository name. This repository's configured project-site target is `https://a4225344a.github.io/Blog/`.

## Deliver the exact validated artifact

The CI workflow runs on pull requests and main pushes. Its validation job uses read-only repository permissions, installs from the lockfile, validates content, runs deterministic tests, checks Astro/TypeScript, and builds the root and production-base variants. Generated-output checks and Chromium tests run against those variants.

Only a main push uploads the `verified-site` artifact. The same workflow contains a deployment job with `needs: validate`, restricted to successful main pushes. It references the `github-pages` environment, whose required reviewers enforce human approval before the job starts. After approval, it rejects a SHA that is no longer main, downloads the artifact from the same run, packages it for Pages, and deploys without checking out or rebuilding the source. Only the deployment job receives Pages write and OIDC permissions. External Actions are pinned to commit hashes.

The maintainer must keep GitHub Actions as the Pages source and preserve branch/environment protection for the human approval gate. Required reviewers are configured in GitHub, not created by YAML. In the CI run, use Review deployments to approve the waiting job. Local success does not demonstrate hosted execution or approval enforcement. The unified workflow change awaits independent review: `IMPLEMENTED_PENDING_INDEPENDENT_REVIEW`.

## Keep V1 small and verifiable

The repository includes pure-logic tests for schemas, references, warnings, ordering, routes, reading time, feeds, and hosting configuration. It also checks workflow structure, verifies built output, and uses Chromium for theme, mobile navigation, and search behavior. These checks provide evidence, not independent review.

V1 deliberately excludes accounts, a database, AI chat or recommendations, quizzes, progress tracking, and an interactive Skill Graph. The most useful next contribution is accurate engineering content that fits the existing model. Add an Article once, reference its stable ID from the correct owner, run validation, and let the static views make it discoverable.
